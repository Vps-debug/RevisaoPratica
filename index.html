📚 Resumão

Requisitos Funcionais

Descrevem o que o sistema deve fazer. Exemplos: cadastrar cliente, consultar notas, marcar consulta, consultar saldo.

Requisitos Não Funcionais

Descrevem características, restrições ou desempenho. Exemplos: carregar em até 3 segundos ou suportar 3.000 usuários.

Critérios de Aceite

Condições objetivas que permitem verificar se uma funcionalidade foi implementada corretamente.

Casos de Teste

Devem considerar situações válidas e inválidas. Ex.: login válido, senha inválida, usuário inválido e campos vazios.

GET

Usado para consultar/obter informações. Ex.: GET /api/produtos.

POST

Usado para enviar dados e, no contexto do simulado, criar registros. Ex.: POST /api/clientes.

Postman

Permite configurar método, endpoint, Body e formato dos dados e analisar status, resposta e evidências.

Análise de Defeitos

Compare o resultado obtido com o resultado esperado. Registre evidências antes de concluir que há defeito.

🔎 Como analisar um requisito?
Pergunte: o que deve acontecer? e como vou verificar? Se o requisito estiver vago, peça esclarecimentos e defina condições verificáveis.
🧪 Antes de registrar um defeito em uma API
  1. Conferir o método HTTP.
  2. Conferir endpoint e ambiente.
  3. Conferir Body e campos obrigatórios.
  4. Conferir formato/estrutura JSON e tipos.
  5. Analisar código de resposta e mensagem de erro.
  6. Guardar evidências para reproduzir o problema.
💡 Exemplos rápidos de critérios verificáveis
  • Agendamento confirmado em até 3 segundos.
  • Usuário com credenciais válidas acessa o sistema.
  • Usuário com credenciais inválidas tem o acesso negado.
  • Cadastro sem nome, e-mail ou senha deve ser bloqueado.
  • CPF já existente não pode ser cadastrado novamente.
